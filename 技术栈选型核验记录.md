**Your hint on this specific point is wrong.** What actually got "split" in 0.8 was the *build* layer:
`cxx-qt-build` (stable builder API) + `qt-build-utils` / `qt-version` / `qt-artifacts` (Qt discovery,
and now Qt downloading).

What *did* change (and why the doc's snippet is dead code): the **location and shape of declarations**,
plus the removal of automatic case conversion.

- 0.5-era (the doc's style): `#[cxx_qt::qobject]` on a struct *inside* the bridge, `impl qobject::T`
  *inside* the bridge, field-level `#[qproperty]`.
- Current (0.6 -> 0.10): the bridge holds **declarations only**. `#[qobject]` on a **type alias**
  (`type MyObject = super::MyObjectRust;`) inside `extern "RustQt"`, properties declared **on the alias**
  as `#[qproperty(TYPE, NAME)]`; the backing Rust struct with matching fields lives **outside** the bridge;
  method/signal signatures declared in `extern "RustQt"` with `#[qinvokable]` / `#[qsignal]`, implemented
  **outside** the bridge in `impl qobject::T` (`qobject` = the bridge module name).
- Signals: `#[qsignal]` goes on a *signature* in an `extern "RustQt"` block (no `unsafe fn` needed);
  you emit by calling it on `Pin<&mut Self>`; base-class signals use `#[inherit]`; generated
  `on_<signal>` / `connect_<signal>` return a RAII `QMetaObjectConnectionGuard`; background threads emit
  through `CxxQtThread`.
- **Breaking and silently dangerous for QML:** since 0.7 there is **no automatic case conversion**.
  Book text: "CXX-Qt <0.7 did automatic case conversion if no `#[cxx_name = "..."]` or
  `#[rust_name = "..."]` is specified. Starting with CXX-Qt 0.7, this is no longer the case! Automatic
  case conversion will be opt-in instead." You write `#[cxx_name = "incrementNumber"]` per item, or opt in
  per-block with `#[auto_cxx_name]` / `#[auto_rust_name]`. **The doc's QML call
  `captureController.startCapture()` against a Rust `start_capture` will not resolve on 0.8+.**
- Additions relevant to us: `#[qml_element]` / `#[qml_uncreatable]` / `#[qml_singleton]` for build-time QML
  registration; `#[base = T]` + `#[cxx_pure]` + `include!` for inheriting real C++ classes (this is the
  escape hatch for subclassing a C++ helper, e.g. an image provider); Rust-side up/down casting for all
  QObject-derived types (0.8).

# 3. Native window escape hatch (HWND) + the transparency/opacity gotchas

## What Qt already does for you (read the Qt source, not folklore)

`src/plugins/platforms/windows/qwindowswindow.cpp` on the `dev` branch of https://github.com/qt/qtbase
(retrieved 2026-10-04, 4161 lines) contains, verbatim:

```cpp
// Set the WS_EX_LAYERED flag on a HWND if required. This is required for
// translucent backgrounds, not fully opaque windows and for
// Qt::WindowTransparentForInput (in combination with WS_EX_TRANSPARENT).
bool QWindowsWindow::setWindowLayered(HWND hwnd, Qt::WindowFlags flags, bool hasAlpha, qreal opacity)
{
    const LONG_PTR exStyle = GetWindowLongPtr(hwnd, GWL_EXSTYLE);
    // Native children are frameless by nature, so check for that as well.
    const bool needsLayered = (flags & Qt::WindowTransparentForInput)
        || (hasAlpha && hasNoNativeFrame(hwnd, flags)) || opacity < 1.0;
    const bool isLayered = (exStyle & WS_EX_LAYERED);
    if (needsLayered != isLayered) { ... SetWindowLongPtr(hwnd, GWL_EXSTYLE, exStyle | WS_EX_LAYERED)
                                   ... else  exStyle & ~WS_EX_LAYERED ... }
```

and at window creation:

```cpp
// make mouse events fall through this window
// NOTE: WS_EX_TRANSPARENT flag can make mouse inputs fall through a layered window
if (flagsIn & Qt::WindowTransparentForInput)
    exStyle |= WS_EX_TRANSPARENT;

// Currently only compatible with D3D surfaces, use it with care.
if (qEnvironmentVariableIntValue("QT_QPA_DISABLE_REDIRECTION_SURFACE"))
    exStyle |= WS_EX_NOREDIRECTIONBITMAP;
```

**Consequence: for the pin window you probably do not need the HWND at all.** All three required
behaviours are first-class Qt window flags/properties reachable from QML, because the QML `Window` type
(`QQuickWindowQmlImpl`) extends `QQuickWindow` extends `QWindow`
(https://github.com/qt/qtdeclarative/blob/dev/src/quick/items/qquickwindowmodule_p.h):

```qml
Window {
    flags: Qt.Window | Qt.FramelessWindowHint            // WS_EX_LAYERED eligibility
           | Qt.WindowStaysOnTopHint                     // topmost
           | Qt.WindowTransparentForInput                // WS_EX_TRANSPARENT (+ forces WS_EX_LAYERED)
    color: "#00000000"                                   // per-pixel alpha background
    opacity: 0.85                                        // QWindow::opacity -> SetLayeredWindowAttributes
}
```

`QWindow` really does expose `opacity : qreal` and `flags : Qt::WindowFlags` as properties
(https://doc.qt.io/qt-6/qwindow.html), and `QQuickWindow::setColor()` internally requests an alpha buffer
(`fmt.setAlphaBufferSize(-1); setFormat(fmt);`) — see
https://github.com/qt/qtdeclarative/blob/dev/src/quick/items/qquickwindow.cpp (the `setColor` body, ~line 3435).
Doc reference for the flags: https://doc.qt.io/qt-6/qt.html#WindowType-enum (`Qt::WindowTransparentForInput`,
`Qt::FramelessWindowHint`, `Qt::WindowStaysOnTopHint`, `Qt::Tool` -> WS_EX_TOOLWINDOW).
Win32 side of the story: https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles
("WS_EX_LAYERED ... windows with the WS_EX_TRANSPARENT bit set ... mouse input falls through").

You still need the real `HWND` for: `WS_EX_NOACTIVATE` (pin must not steal focus — no Qt equivalent),
`SetWindowDisplayAffinity` (exclude pins from your own captures), DWM shadow / rounded-corner control,
appearing above full-screen games, `WS_EX_TOOLWINDOW` alt-tab suppression nuances, and drag-region tricks.

## How to get the HWND — CXX-Qt

`QWindow::winId()` returns `WId`, which **is** the `HWND` on Windows; cast and hand it to `windows-rs`.
But **cxx-qt-lib binds no window class at all.** Verified by enumerating the crate on `main`:
`cxx-qt-lib/include/gui/` = qcolor, qfont, qgenericmatrix, qguiapplication, qimage, qpainter, qpainterpath,
qpen, qpolygon, qpolygonf, qquaternion, qregion, qvector2d/3d/4d — **no `qwindow.h`**;
`cxx-qt-lib/include/qml/` = qqmlapplicationengine, qqmlengine, qqmlimageproviderbase only;
`quickcontrols` = qquickstyle. A repo-wide code search for `winId` in KDAB/cxx-qt returns nothing.
(https://github.com/KDAB/cxx-qt/tree/main/cxx-qt-lib/include)

So the supported route is the doc's own `qt/cpp/native_window_helper.cpp` idea, but it is **mandatory**, not
optional: one C++ translation unit compiled by Cargo, e.g.

```cpp
// native_window_helper.cpp  -> added in build.rs with CxxQtBuilder::cpp_file("native_window_helper.cpp")
void apply_pin_style(QQuickWindow *w, bool clickThrough, bool noActivate, bool topmost) {
    HWND hwnd = reinterpret_cast<HWND>(w->winId());
    LONG_PTR ex = GetWindowLongPtr(hwnd, GWL_EXSTYLE);
    ... SetWindowLongPtr(hwnd, GWL_EXSTYLE, ex | WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE) ...
    SetWindowPos(hwnd, topmost ? HWND_TOPMOST : HWND_NOTOPMOST, 0,0,0,0, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE);
}
```

declared in the bridge as `unsafe extern "C++" { include!("native_window_helper.h"); fn apply_pin_style(...); }`
(or via `extern "C++Qt"` / `#[base = T]` if you want to subclass). To reach the `QQuickWindow*`, either expose
a `Q_INVOKABLE` on a small C++ QObject and call it **from QML** (QML converts the `Window` to
`QQuickWindow*` automatically), or enumerate `QGuiApplication::topLevelWindows()` inside the helper.
Build-script note: 0.8 renamed `CxxQtBuilder::qobject_header` to `cpp_file` and *allows compiling .cpp files* —
that rename alone will break anyone following pre-0.8 tutorials
(https://github.com/KDAB/cxx-qt/releases/tag/v0.8.0).

## How to get the HWND — qtbridge (official Qt Bridge for Rust)

**You currently cannot.** The entire GUI surface of the crate is
`crates/qtbridge-type-lib/src/gui/` -> **`qguiapplication` only** (enumerated the `dev` tree, 669 paths:
no QWindow, no QQuickWindow, no QImage, no window handle, no image provider), the README's selling point is
"without writing any C++ code", and there is no `winId` anywhere in the repo
(https://github.com/qt/qtbridge-rust). For a product whose core feature is click-through + topmost +
alpha pins, **this is a hard blocker**, not a papercut. It would also make you dependent on Qt Company
accepting a native-handle PR.

## Gotchas with transparent / per-window-opacity Qt Quick windows on Windows

1. **Qt owns `WS_EX_LAYERED` and will remove it.** `setWindowLayered()` is called from
   `setWindowOpacity()` and computes `needsLayered` each time; if you hand-patched `WS_EX_TRANSPARENT`
   without setting `Qt::WindowTransparentForInput`, the moment `opacity` goes back to 1.0 on a window with no
   alpha/native frame, Qt clears `WS_EX_LAYERED` and **your click-through silently stops working**
   (WS_EX_TRANSPARENT needs layered). Make the Qt flag the source of truth, or re-apply on every
   flags/opacity change.
2. **Per-pixel alpha requires frameless.** `needsLayered` gates the `hasAlpha` branch on
   `hasNoNativeFrame(hwnd, flags)` (`WS_CHILD || Qt::FramelessWindowHint`). Long-standing Windows reports of
   "transparent background renders black" resolve by adding `FramelessWindowHint`
   (e.g. https://m.blog.csdn.net/itworld123/article/details/118055216) — consistent with the source.
3. **GPU backend + window opacity = redirection.** `setWindowOpacity()` uses
   `UpdateLayeredWindow(ULW_ALPHA)` only for **non-accelerated** windows, otherwise
   `SetLayeredWindowAttributes(hwnd, 0, alpha, LWA_ALPHA)` — a *uniform*, whole-window alpha applied by DWM,
   which composites against the redirection surface. Qt Quick's default RHI on Windows is **Direct3D 11**
   (https://doc.qt.io/qt-6/qtquick3d-requirements.html: "The defaults are currently Direct3D 11 for Windows,
   Metal for macOS, OpenGL elsewhere"). Practical implication for pins: prefer `Item.opacity` on the content
   over `Window.opacity` where you can, budget for a software-renderer fallback
   (`QT_QUICK_BACKEND=software` / `QQuickWindow::setGraphicsApi(QSGRendererInterface::Software)`), and test
   100%/125%/150%/200% + NVIDIA/AMD/Intel + RDP before promising "smooth opacity slider".
4. **Black 1-2px edges / DWM residue** around frameless translucent Quick windows is a recurring report
   (https://m.blog.csdn.net/adsd1233123/article/details/157320003 , 2026-02, which solves it with
   `QQuickWindow::setDefaultAlphaBuffer(true)` before the first window or by adopting `qwindowkit`).
   Note `alphaBuffer` is **not** a QML `Window` property — only the static
   `QQuickWindow::setDefaultAlphaBuffer(bool)`, whose doc says "In any application which expects to create
   translucent windows, it's necessary to set this to true **before creating the first QQuickWindow**"
   (https://github.com/qt/qtdeclarative/blob/dev/src/quick/items/qquickwindow.cpp ~line 3463). In a
   QQmlApplicationEngine app you therefore need a C++/`main.rs`-time hook, another reason a C++ shim exists.
5. **Do not set `WS_EX_NOREDIRECTIONBITMAP` casually** — Qt gates it behind an env var with the comment
   "Currently only compatible with D3D surfaces, use it with care", and no-redirection breaks the
   layered/`SetLayeredWindowAttributes` opacity path.
6. **`winId()` forces native creation**; the handle is only meaningful after the window is created/shown, so
   apply styles from `Component.onCompleted` **after** `visible = true`, not from a Rust constructor.
7. Qt Widgets-only trap (for the overlay, if you follow section 4's advice): in the Widgets stack, giving a
   child widget its own native window destroys the single-surface "directui" layered window and hence
   translucency — never parent a `QWindow`/`QOpenGLWidget` inside a translucent frameless overlay widget
   (community analysis of `QWindowsBackingStore::flush`: https://blog.csdn.net/zchl159/article/details/103817624).
   QQuickWidget/QWebEngineView inside a translucent QWidget window are the usual offenders.

**Verdict (Q3): the Win32/`WS_EX_*` work the doc plans for is largely unnecessary for click-through, topmost
and opacity — Qt implements exactly those three (`Qt::WindowTransparentForInput`,
`Qt::WindowStaysOnTopHint`, `QWindow::opacity`) and manages `WS_EX_LAYERED` for you; keep one small C++ shim
for `WS_EX_NOACTIVATE`/DWM/display-affinity and get the HWND via `QWindow::winId()`. CXX-Qt gives you that
shim; qtbridge does not. The real Windows-specific risks are the accelerated-opacity redirection path, the
frameless requirement for per-pixel alpha, and black-edge artifacts — none of which the design doc mentions.**

# 4. Screenshot-overlay feasibility, and whether Qt is even right for the mask

## Qt's own docs say the "one giant fullscreen window" design is wrong

From https://doc.qt.io/qt-6/highdpi.html (the page renders as **"Qt 6.12"**, i.e. current dev docs):

> "Qt scales the screen size (resulting in a 'smaller' screen for positive scale factors), but doesn't change
> the screen position. This produces **islands-of-screens type virtual desktop geometry**. Application code
> should not assume that a position immediately adjacent to and outside one screen is a valid position on the
> neighboring screen. Instead, get the screen list using `QGuiApplication::screens()` and use that list to
> reason about available screen geometry."

Also on that page: "Qt 6 is **Per-Monitor DPI Aware V2** by default" on Windows; `QWindow::devicePixelRatio()`
tracks "the device pixel ratio of the window when moved between displays"; "Integer scale factors ... are
preferred for best results ... [fractional] may not give good visual results", with
`QGuiApplication::setHighDpiScaleFactorRoundingPolicy()` / `QT_SCALE_FACTOR_ROUNDING_POLICY` as the lever, and
`QT_SCALE_FACTOR` + the `dprgadget` manual test app (`qtbase/tests/manual/highdpi/dprgadget`) for verification.
Signal that this area is still moving: `QQuickWindow` gained a `devicePixelRatio` property only in
**Qt 6.11** (`Q_PROPERTY(qreal devicePixelRatio ... REVISION(6, 11))`,
https://github.com/qt/qtdeclarative/blob/dev/src/quick/items/qquickwindow.h).

**Therefore: per-monitor-DPI fullscreen translucent overlays are feasible in Qt only as *N windows, one per
QScreen*, each rendered at its own DPR, with capture done in physical pixels and UI in device-independent
pixels.** A single borderless window spanning the merged virtual desktop (the naive "one mask over
everything") is precisely the pattern Qt documents as unreliable when scale factors differ. The doc's claim
(section 2.1) that 多显示器截图遮罩 + DPI are "Qt 强项" is true **only under that architecture**, and its
section 5 `CaptureOverlay.qml` (singular) implies the wrong one.

## Real-world Qt evidence (for)

- **Flameshot** — https://github.com/flameshot-org/flameshot , **31,077 stars**, last push **2026-10-03**,
  "C++/Qt cross-platform screenshot tool" (HelloGitHub 126 roundup, 2026-09-28:
  https://juejin.cn/post/7689599510956507136). Its source is the exact pattern above:
  `src/widgets/capture/capturewidget.cpp` sets
  `Qt::WindowStaysOnTopHint | Qt::FramelessWindowHint` (+ `Qt::BypassWindowManagerHint` on X11) and iterates
  screens using `selectedScreen->geometry().topLeft()` per screen; `src/tools/pin/pinwidget.cpp` (the
  Snipaste-style pin) uses `WindowStaysOnTopHint | FramelessWindowHint` + `WA_TranslucentBackground` +
  `WA_DeleteOnClose`; `src/tools/pin/`, `src/widgets/capture/magnifierwidget.cpp`, `overlaymessage.cpp` exist.
  Note **CMake >= 3.22** and Qt6 CMake integration in its `CMakeLists.txt`.
- **ksnip** — https://github.com/ksnip/ksnip , **3,347 stars**, last push 2026-10-01, "cross-platform
  screenshot and annotation tool"; `src/gui/modelessWindows/pinWindow/PinWindow.cpp` uses
  `Qt::FramelessWindowHint | Qt::WindowStaysOnTopHint | Qt::CoverWindow` + `Qt::WA_TranslucentBackground`, and
  the annotation engine is the separate QWidget-based `kImageAnnotator` library (submodule).
- **Snipaste-class tools generally**: 30k-star Flameshot shipping pin-to-screen + magnifier + mosaic in Qt is
  the strongest available proof that Qt's window/compositing layer is adequate for this product.
- Both of the above use **Qt Widgets + QPainter for the overlay, toolbar and annotation canvas**, and Qt
  Widgets for the pin. Nobody in this product category is doing the mask in QML. The QML/Quick-for-everything
  framing in doc section 3.1 is over-optimistic; 3.2's "special screenshot windows in Widgets" hedge is
  actually the *main* path, not an exception.

## Real-world Rust evidence (against "Rust + Qt is the obvious combo")

Searching GitHub for Rust screenshot/pin tools (2026-10-04, `gh api search/repositories`) returned **no
Rust+Qt tool at all**; the population is: `glint-screenshot` (Rust + GTK4 + Cairo, GNOME/Wayland),
`RSnap` (Tauri + Rust, Windows screenshot+pin), `Pincer` (Rust + egui), `HydroShot` (pure Rust, 14 annotation
tools + OCR + pin), `PinShot`/`tool-helper` (Tauri 2 + React). A `cxx-qt` + screenshot query returned nothing.
Conclusion: Qt is not *wrong* for this, but **you would be the first production Rust+Qt screenshot tool you can
find**, so the bridge (not Qt) is where the unproven risk sits.

**Verdict (Q4): Qt is the right engine for the capture mask, with a corrected architecture — one borderless,
frameless, translucent overlay window per QScreen, physical-pixel capture (Windows Graphics Capture / DXGI
duplicated surface via `windows-rs`) + device-independent-pixel drawing, per-screen DPR tracked, and the
annotation canvas implemented in C++ (QWidget/QPainter or QQuickPaintedItem) rather than in QML/Canvas. Keep
`QT_SCALE_FACTOR_ROUNDING_POLICY`, `dprgadget`, and a mixed-DPI two-monitor rig in CI.**

# VERDICT

**Stick with Qt 6 + QML + CXX-Qt. Do not switch to "official Qt bindings", and do not change stacks.**
But re-scope three decisions the doc got wrong: (1) the bridge code and build story in section 6 are two
major versions out of date; (2) sections 3.1/5 put too much of the hard UI in QML — the mask, pin and
annotation canvas want C++/Qt Widgets or a C++-rendered Quick item, with QML reserved for chrome (settings,
history, popovers, toolbars); (3) section 10.2's Win32 `WS_EX_*` worklist is mostly already implemented by Qt,
so the native layer shrinks to a single small C++ shim. Rejecting `qtbridge` (0.3.0-beta, LGPL-3.0-only/commercial,
Qt >= 6.10 hard pin, no QWindow/QImage/handle bindings, and *itself built on cxx-qt 0.10*) and rejecting the
`qt_core`/`qt_gui`/`qtwidgets` crates (dead since 2020/2023, no Qt 6 line) is not a preference — those options
do not exist in a consumable form.

## 5 concrete build/runtime risks to put in the implementation plan

1. **Bridge API drift with no 1.0.** CXX-Qt is 0.10.0 (2026-08-24) and its README still says "in early
   development and the API changes frequently"; 0.6 rewrote the declaration model, 0.7 removed automatic
   camelCase conversion (silent QML binding breakage), 0.8 renamed build APIs
   (`qobject_header` -> `cpp_file`, one QML module per builder, multi-crate interfaces).
   *Plan:* pin `cxx-qt = "=0.10.0"` / `cxx-qt-lib = "=0.10.0"` / `cxx-qt-build = "=0.10"` with
   `link_qt_object_files`, add an upgrade ticket per minor, and check a "current API cheat-sheet" into the repo
   generated from the pinned version's book — never from `Rust_Qt_Snipaste类工具技术方案.md`.
2. **"Rust-only" is a false premise; you will ship and maintain C++.** cxx-qt-lib binds no `QWindow`,
   `QQuickWindow`, `QQuickView`, `QQuickPaintedItem` or a usable `QQuickImageProvider` subclass path (verified
   include inventory; only `QQmlImageProviderBase` + `QQmlEngine::addImageProvider` plumbing landed in 0.9.0).
   *Plan:* budget a C++ TU per capability (window helper, painted overlay item, image provider) in the
   `qt-bridge` crate, a team member who can debug MSVC C++ alongside Rust, clang-format + `/utf-8` +
   C++17 settings in CI, and an explicit spike to prove Rust-implemented `requestImage()` before committing to
   doc section 7.3.
3. **Windows transparency/opacity correctness on the GPU path.** Qt Quick defaults to Direct3D 11 on Windows;
   Qt only sets `WS_EX_LAYERED` for `WindowTransparentForInput` / frameless+alpha / `opacity < 1.0`, and for
   accelerated windows uses `SetLayeredWindowAttributes(LWA_ALPHA)` (uniform, DWM-redirection-based) instead of
   `UpdateLayeredWindow`. Hand-applied `WS_EX_TRANSPARENT` gets its layered style stripped; per-pixel alpha
   needs frameless; `setDefaultAlphaBuffer(true)` must run before the first window; black 1-2px edges are a
   recurring report. *Plan:* a 2-week prototype on Intel+NVIDIA+AMD, single+multi-monitor, 100/125/150/200%,
   HDR and non-HDR, RDP; `QT_QUICK_BACKEND=software` kill switch; prefer `Item.opacity` over `Window.opacity`;
   treat pin opacity as a matrix-tested feature, not a slider.
4. **Multi-monitor/DPI overlay architecture is a product-shaping constraint, not a bug to fix later.**
   Qt documents "islands-of-screens" virtual-desktop geometry and forbids assuming adjacency; integer scaling
   is "preferred"; `QQuickWindow.devicePixelRatio` only became a property in Qt 6.11.
   *Plan:* one overlay window per `QScreen` from day 1, physical-pixel capture buffers, `QWindow::devicePixelRatio`
   change handlers, runtime DPI-change + hot-plug + orientation-change test cases in the MVP acceptance list,
   `QT_SCALE_FACTOR`/`dprgadget` in CI, and `setHighDpiScaleFactorRoundingPolicy` as an explicit
   product decision (crispness vs. true 125%/150% fidelity on the magnifier/pixel grid).
5. **Licence + packaging + memory peak.** The bridge is MIT OR Apache-2.0, but Qt itself is LGPL-3.0/GPL-3.0 or
   commercial: on Windows you must ship `windeployqt` output (platform plugin, `QtQuick`/`QtQuickControls2` QML
   modules, image-format plugins) and honour LGPL relinking/attribution, or buy a seat; any adoption of
   `qtbridge` later would add `LicenseRef-Qt-Commercial OR LGPL-3.0-only` on the bridge layer. Runtime: a 4K
   RGBA frame is ~31.6 MiB, the doc's own `Vec<u8> -> QByteArray -> QImage -> QML -> texture` chain multiplies
   that, and pins keep originals *and* processed copies. *Plan:* decide dynamic-link Qt + commercial-licence
   trigger before MVP; forbid pixel payloads in bridge signatures (IDs / `Arc<FrameBuffer>` handles only);
   add an RSS/frame-copy budget test (e.g. 3 monitors x 4K, 20 pins, <500 MB) as a release gate.
